# Nebula 核心架构公理：L1/L2 严格分层详解

在 Nebula 的哲学中，**公理 B（生命周期严格分层）** 是为了彻底解决 GUI 开发中常见的“状态混乱”和“内存泄漏”问题。我们将所有数据根据其**生命周期**和**变更频率**，严格划分为两个层级：

---

## 1. L1 层：持久状态 (Persistent State)

**定义**：跨帧存活的数据。如果用户不操作，这些数据在 100 帧甚至 1 小时后依然存在。

*   **归属**：属于 `Visual` 规格或 `Context` 状态。
*   **内存分配**：静态分配（Static）或在应用启动时分配。**严禁在渲染循环中分配 L1 内存**。
*   **例子**：
    *   `InputVisual.gap_buf`：输入框里的字符内容（你打的字不能下一帧就没了）。
    *   `InputContext.selection_anchor`：选区的起始点。
    *   `CardVisual.pos`：组件在屏幕上的位置。
*   **哲学隐喻**：它是应用的“灵魂”和“记忆”。

---

## 2. L2 层：帧级瞬时数据 (Frame-level Transient Data)

**定义**：仅在当前帧有效的临时数据。一旦当前帧渲染结束，这些数据就彻底失效，内存被回收。

*   **归属**：属于渲染过程中的中间计算结果。
*   **内存分配**：**栈上（Stack）**或 **Frame Arena（帧分配器）**。
*   **例子**：
    *   `advances` 数组：每个字符的 X 坐标偏移。如果窗口缩放或字号变了，这些坐标下一帧就全变了，所以没必要存着。
    *   `tmp_flat_text`：为了传给 C 接口而临时展平的字符串。
    *   命中测试的中间结果。
*   **哲学隐喻**：它是应用的“思维过程”和“视觉残像”。

---

## 3. 为什么必须严格分层？（解决架构张力）

在 Phase 3.6.2 之前，Nebula 曾出现过 **“L1/L2 渗透”** 的架构坏味道：

### 错误示范（渗透）：
为了方便，把 `advances`（L2）存进了 `InputVisual`（L1）。
*   **代价 1（内存浪费）**：每个输入框无论是否显示，都要永久占用 1KB 内存存坐标。
*   **代价 2（同步地狱）**：如果用户改了字号，你必须手动去更新这个 `advances` 数组，否则渲染就错位了。

### 正确示范（分层）：
`InputVisual` 只存字符（L1）。当鼠标点击时：
1.  在**栈上**临时开辟一块空间计算 `advances`（L2）。
2.  完成命中测试，得到光标位置。
3.  函数返回，`advances` 内存自动回收。
*   **收益**：内存占用降低 90%，且天然支持响应式（每次都用最新的字号实时计算）。

---

## 4. 总结对比表

| 特性 | L1 层 (Persistent) | L2 层 (Transient) |
| :--- | :--- | :--- |
| **存在意义** | 业务逻辑的真实状态 | 渲染表现的中间过程 |
| **生命周期** | 与组件/应用同生共死 | 始于帧开始，终于帧结束 |
| **存储位置** | Record 字段 / 全局变量 | 栈 (Stack) / Frame Arena |
| **管理方式** | 显式管理 | 自动回收 (Reset) |
| **Nebula 原则** | **严禁依赖 L2** | **严禁污染 L1** |

> **一元规则**：如果一个数据可以通过 L1 状态在 < 1ms 内计算出来，那么它就不应该被存储在 L1 中，而应该在需要时作为 L2 数据即时生成。

这就是为什么在 Phase 3.6.3 的方案中，我坚持选区高亮的矩形坐标不存储，而是每帧即时计算的原因。这保证了 Nebula 的核心永远是轻量且确定性的。
