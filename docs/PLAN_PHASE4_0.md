# Phase 4.0：编译期公理校验器（Axiom Validator）

**状态：已完成** | **完成日期：2026-04-26** | **回归测试：28/28 通过**

---

## 1. 目标与愿景

Phase 4.0 的核心任务是将 Nebula 的架构哲学（三大公理与七大不变量）从"文档共识"升级为"编译器强制约束"。基于**注册表质量门（Registry Quality Gate）**方案，利用 Lua 宏在 S1 阶段的全局可见性，在代码生成之前对元数据进行深度语义校验。

**核心设计原则（与原规划的关键差异）**：采用**只读断言（Read-only Assertions）**模式——校验器只检查、只拦截、不修改任何注册表状态。这是对原规划任务 B"强制合并 type_groups"的降级修正，原因详见第 3.2 节。

---

## 2. 校验架构

引入独立模块 `src/derive/axiom_validator.lua`，在两个关键入口挂载校验钩子：

- **Visual 级校验**：在 `nebula_derive` 的 `nebula_parse_shape` 之后触发，校验单个 Visual 类型的字段是否违反生命周期公理。
- **App 级校验**：在 `nebula_app_generate` 的代码生成之前触发，校验组件间的组合关系、管线路径一致性及静态展开约束。

---

## 3. 三大任务实施详情

### 3.1 任务 A：生命周期类型白名单（公理 B 约束）✅

**目标**：防止 L2（帧级）数据泄漏到 L1（持久层 Visual Record）。

**L1 类型白名单**：`float32` / `Vec2` / `Vec4` / `Color` / `bool` / `uint8` / `uint16` / `uint32` / `int32`

**拦截项**：
- `NebulaTextMesh`（L2 帧级文本网格）→ 应通过 `nebula_app_register_text` 注册
- `GapBuffer`（L2 帧级 Gap Buffer）→ 应通过 `editable` 原语自动注入
- `NebulaArena`（L0 永久层 Arena）→ 不应出现在 L1 Visual Record 中
- 任何指针类型（`*T`）→ 违反 L1 持久层的值语义要求

**错误标识**：`[Axiom-B 违规]`，附带具体字段名、类型名和修复建议。

### 3.2 任务 B：只读管线路径冲突检测（公理 C 约束，降级版）✅

**目标**：检测同一 App 内不同 Visual 类型的管线路径是否存在结构性冲突。

**与原规划的差异**：原规划要求"强制合并 type_groups"，实际实现降级为"只读冲突检测"。

**降级原因**：
1. `pipeline_factory.lua` 的三条路径（standard_instanced / textured_vertex / shadow_multipass）结构差异巨大，强行自动合并极易引发难以调试的 WebGPU 绑定冲突。
2. 让校验器自动修改注册表状态违反了单一职责原则，使调试困难。
3. 只读断言更符合 Nebula 的"阶段封闭性"哲学——S1 校验阶段不应产生 S1 副作用。

**实现**：检测同一 pipeline_name 是否被不同路径类型的 Visual 共享，发现冲突时报错，要求开发者手动修正。

**错误标识**：`[Axiom-C 违规]`，附带冲突的管线名、Visual 类型和路径类型。

### 3.3 任务 C：静态展开验证（不变量 I1 约束）✅

**目标**：确保所有组件名为合法静态标识符，Slot 的 max_instances 为编译期正整数常量。

**校验规则**：
- 组件名（components/slots/texts/shadows）必须匹配 `^[%a_][%a%d_]*$`（合法 Nelua 标识符）
- Slot 的 `max_instances` 必须为正整数（`> 0` 且 `== math.floor(max_instances)`）

**错误标识**：`[Invariant-I1 违规]`，附带违规组件名和修复建议。

## 7. 验收标准达成情况

1. **拦截成功率** ✅：所有故意违反公理的测试用例均导致编译失败，错误信息精确定位到具体字段名和违反的公理编号。
2. **零性能损耗** ✅：校验过程仅发生在 S1 编译期（Lua 宏执行阶段），生成的 S2 运行时二进制文件不含任何校验逻辑。
3. **错误提示友好度** ✅：编译错误指明具体的组件名、字段名、违反的公理编号，并附带修复建议。
