# 架构评估：L1/L2 分层是 Nebula 的终极最优解吗？

## 1. 行业对比：三种主流路线的博弈

要评估 Nebula 的优劣，必须看它的对手们：

| 架构路线 | 代表作 | 策略 | 优缺点 |
| :--- | :--- | :--- | :--- |
| **全量持久 (Full Retained)** | Qt, DOM (Web) | 所有数据都是 L1。修改一个属性，框架帮你同步所有关联。 | **优**：开发直观。**劣**：内存爆炸，同步逻辑（Dirty flags）极其复杂，极难并行。 |
| **全量即时 (Full Immediate)** | Dear ImGUI | 几乎没有 L1，每一帧从零开始。 | **优**：极其简单。**劣**：CPU 开销随 UI 复杂度线性增长，难以处理复杂的交互状态（如长文本编辑）。 |
| **分层即时 (Layered Immediate)** | **Nebula**, GPUI | **L1 存意图，L2 算表现**。 | **优**：内存确定性，高性能，天然支持多线程。**劣**：对架构师的功力要求极高。 |

---

## 2. 为什么它是“最优解”？（核心收益）

### A. 彻底消灭“缓存失效”地狱
在传统 GUI 中，最难的 Bug 往往是：*“我改了状态 A，但界面上依赖 A 的 B 没更新”*。
在 L1/L2 架构下，B 根本不存储，它是每帧根据最新的 A 现算的。这从物理定律上**彻底消灭了“界面不同步”类 Bug**。

### B. 极致的内存确定性
由于 L1 是静态或预分配的，Nebula 应用在启动一秒后，它的**持久内存曲线就是一条直线**。这对于嵌入式系统、高频交易终端或极致性能的游戏引擎来说，是梦寐以求的特性。

### C. 完美的并行潜力（并行公理）
L2 计算通常是**纯函数（Pure Function）**。
例如：将 1000 个文本块的 L1 字符转换为 L2 排版坐标。由于 L2 之间互不依赖，我们可以极其轻松地将这个任务分发给 16 个 CPU 核心，甚至直接丢给 GPU Compute Shader。

---

## 3. 它的“代价”是什么？

**重复计算开销**。
如果界面 1 分钟没动，Nebula 依然在每秒 60 次地计算那些没变的坐标。
*   **Nebula 的对策**：我们的排版算法（如 `nebula_text_compute_advances`）被优化到了纳秒级。对于现代 CPU 来说，几百个字符的加法运算开销远低于一次内存抖动（Cache Miss）。**我们用微小的、确定的计算开销，换取了巨大的、不确定的内存管理开销。**

---

## 4. 未来扩展性评估

### Q1: 如果 UI 变得极其复杂（如 10 万行代码编辑器）？
**答案**：L1/L2 依然有效。我们会引入 **"L1.5"（局部缓存）**。但与传统架构不同，这个缓存会被标记为 `TransientCache`，它可以被随时丢弃而不会损坏业务逻辑。

### Q2: 跨平台渲染（WASM/Android/iOS）？
**答案**：这是 L1/L2 的主场。因为 L1 是纯数据，我们可以极其容易地将 L1 序列化并传给不同的后端，而 L2 则由各端根据自己的屏幕特性（DPI、字体引擎）即时生成。

---

## 5. 最终结论

**是的，它是最优解。**

它不是“最容易写”的解，但是**“上限最高”**的解。
它选择了将复杂度留在**编译期（元编程）**，将确定性留给**运行时**。

对于 Nebula 这样一个追求“GUI 编译器”目标的系统来说，L1/L2 分层不是一种选择，而是一种**信仰**。它确保了无论 Nebula 未来长到多大，它依然能保持那种“透明、可控、极速”的初衷。
